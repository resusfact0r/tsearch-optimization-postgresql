# FTS uid experiment - замена строковых лексем на целочисленные идентификаторы

## Ход исследования (сводка)

| Этап | Вопрос | Как проверяли | Результат | Статус |
|---|---|---|---|---|
| 1 | Даст ли выигрыш замена лексем на 4-байтные id? | SQL-прокси: base36-строки в обычном `tsvector`, 500K документов | −19% размера; `ts_rank`/`ts_rank_cd` x1.08–1.44 по времени запроса | выигрыш есть, но его причина объяснена неверно (см. 2.1) |
| 2 | Сколько дают настоящие int4? | C-расширение `uidfts`: `uidvector`, `uidquery`, `@@`, `ts_rank`, `ts_rank_cd`; совпадение с ядром побитово | −32% размера; по времени x1.7–4.6 в узкой таблице, ~x1.3 с текстом документа в той же строке | сделано |
| 2.1 | Что ускоряется в самих функциях, а что нет? | данные без TOAST (`STORAGE PLAIN`), время + callgrind (инструкции, кэш) | прокси вычисления **не** ускоряет (+0–3% инструкций), выигрывает только на промахах кэша; uidvector: `@@` в 2.1–2.4 раза, `ts_rank` в 1.9 раза меньше инструкций; в `ts_rank_cd` ~50–75% времени — выделение и обнуление памяти | измерено |
| 2.2 | Какую долю занимает TOAST внутри вызова и в топ-k запросе? | callgrind на таблицах с TOAST, подсчёт чтений из TOAST по вызывающим функциям | одно чтение из TOAST ≈ 15–17 тыс. инструкций (в 8 раз дороже всего `ts_rank`); с текстом в строке TOAST — 86–97% стоимости вызова; при последовательном сканировании совпавшие строки читаются из TOAST дважды, но это ~4% стоимости | измерено |

**Выводы на сейчас:**
1. Замена строк на int4 вдвое сокращает вычисления в `@@` и `ts_rank`: сравнение
   строк исчезает полностью, поиск лексемы в 1.8–2.5 раза дешевле.
2. В реальной таблице время определяет не вычисление, а чтение вектора из TOAST
   (86–97% стоимости вызова). Поэтому итоговый выигрыш uidvector там ~x1.25–1.38,
   и он идёт в основном от того, что меньший вектор реже выносится в TOAST.
3. Ещё больший вклад — индекс: топ-10 через GIN в 14–150 раз быстрее
   последовательного сканирования. GIN для `uidvector` пока нет — это главный
   пробел для сравнения «запрос целиком».
4. `ts_rank_cd` ускоряется слабее (x1.25–1.33): ~50–75% его времени — выделение
   и обнуление рабочего массива на 32 КБ на узел запроса, от представления лексем
   это не зависит. Это отдельная оптимизация, применимая и к ядру PostgreSQL.

## Мотивация

PostgreSQL FTS хранит лексемы в `tsvector` как переменные строки. При поиске и ранжировании
документов ядро делает бинарный поиск по лексемам с побайтовым сравнением строк. Гипотеза:

> Если заменить строковые лексемы на фиксированные 4-байтные целочисленные идентификаторы,
> то уменьшится размер `tsvector`, ускорится проход по GIN/GIST, и - главное - ускорятся
> функции `ts_rank` / `ts_rank_cd`, которые индекс не используют и работают целиком на CPU.

Настоящий C-extension пока не пишется. Вместо этого делается прокси: лексемы
заменяются 4-символьными строками из алфавита `0-9a-z` (base36). Ширина ключа та же -
4 байта, - поэтому прокси является честным нижним порогом для реального int4-extension.

> **Проверено на этапе 2.1 — неверно в части CPU.** Прокси не сокращает
> вычисления: сравнений строк столько же, инструкций на 0–3% больше. Нижней
> оценкой он служит только для эффектов размера (TOAST, кэш).

## Методология

### Прокси-кодирование

Вместо настоящего `int4` используется строка из 4 символов алфавита `0-9a-z` (36 символов,
36^4 = 1 679 616 уникальных значений). Алфавит выбран строчным потому, что `to_tsquery('simple', ...)`
приводит токены к нижнему регистру - заглавные символы вызывали бы коллизии.

Пример: лексема `"initi"` (самая частая в корпусе) получает id 1 -> encoded = `"0001"`.

Позиции и веса слов в `tsvector` сохраняются полностью, поэтому прокси-вектор
семантически эквивалентен исходному: проверяется верификационным шагом.

### Параметры бенчмарка

| Параметр | Значение |
|---|---|
| PostgreSQL | 14.23 |
| Корпус | 10 000 документов, 50-200 слов, синтетика из `/usr/share/dict/words` |
| Конфигурация FTS | `english` (для baseline), `simple` (для прокси-запросов) |
| JIT | выключен (`SET jit = off`) |
| Параллелизм | выключен (`max_parallel_workers_per_gather = 0`) |
| Кэш | тёплый (всё в `shared_buffers`) |
| Повторений | 10 прогонов на каждую точку, медиана |
| GIN vs GIST | замеряются раздельно: перед GIN-замером дропается GIST, и наоборот |

### Запросная нагрузка

- **single** - 500 запросов по одному термину (топ-500 по частоте в корпусе)
- **and2** - 200 AND-запросов из двух термин
- **phrase** - 200 фразовых запросов (`<->`)

Для каждого текстового запроса строится его прокси-двойник: лексемы заменяются
закодированными id, конфигурация меняется с `english` на `simple`.

## Интерпретация результатов

### Ранжирование: гипотеза подтверждается, эффект устойчив

`ts_rank` и `ts_rank_cd` ускоряются на **8-44%** как при тёплом, так и при холодном кэше.
Ускорение при холодном кэше даже чуть выше: меньший `tsvector` -> меньше страниц читается
с диска при TABLESAMPLE-сканировании + быстрее CPU-сравнения. Это сугубо CPU-эффект,
не зависящий от I/O - функции ранжирования индекс не используют.

> **Проверено на этапе 2.1 — «сугубо CPU-эффект» неверно.** По callgrind прокси
> исполняет на 0–3% *больше* инструкций, чем tsvector, во всех сценариях:
> сравнений столько же, каждое — тот же `tsCompareString` + `memcmp`. Выигрыш
> прокси по времени складывается из двух вещей, обе — следствие меньшего размера:
> (1) реже выносится в TOAST и быстрее извлекается (этап 2); (2) меньше промахов
> кэша данных: в `ts_rank` с двумя термами 0.61 промаха L1 на вызов против 2.43.
> Ускорение самих вычислений прокси не дал. См. [Этап 2.1](#этап-21-чистый-cpu-замер-без-toast-и-callgrind).

### GIN: разница в пределах шума на 10K корпусе

Однотерминный GIN-поиск показывает x0.99-1.00 - практически без разницы. Причина: GIN
posting-листы по размеру примерно одинаковы (7968 vs 7856 kB, разница 1.4%), а 10K документов
полностью помещаются в кэш. Значимая разница ожидалась на 500K+ документов, предполагалось что индекс не
помещается в память и I/O-чтения более коротких posting-листов дадут измеримый выигрыш, но по результату выигрыш получился небольшой: x1.00-1.04 

> **Не проверялось.** Причины поведения GIN не измерялись; для `uidvector`
> GIN-опкласса пока нет.

### GIST: структурное замедление для AND-запросов

GIST замедляется для AND/phrase как в тёплом (x0.78), так и в холодном (x0.80) режиме.
Это не I/O-артефакт - разрыв одинаков при любом состоянии кэша. Скорее всего здесь структурная причина:
GIST использует сигнатурное хэширование лексем для построения bitmap. Base36-идентификаторы
вида `0001`, `0002`, … сконцентрированы в начале алфавита и хуже распределяются по
хэш-пространству, чем естественные английские слова. Это приводит к большему числу
false-positive при проверке AND-условия и дополнительным heap-fetches для recheck.

> **Не проверялось.** Объяснение через хэш-сигнатуры — гипотеза; число
> false-positive / recheck не измерялось.

### Ограничение прокси

Прокси использует строки base36 (4 байта содержимого + 1 байт varlena-заголовок = 5 байт)
вместо настоящего `int4` (4 байта без заголовка). Кроме того, сравнение строк - это `memcmp`,
тогда как int4 сравнивается одной машинной инструкцией. Поэтому если прокси даёт X% ускорения - реальный int4-extension даст не меньше X%.

> **Проверено на этапе 2.1.** Вывод «int4 даст не меньше» подтвердился:
> `uidvector` быстрее прокси во всех сценариях. Но обоснование было неверным:
> прокси вычисления не сокращал (сравнений строк столько же, инструкций на 0–3%
> больше). Значит, прокси нельзя считать нижней оценкой выигрыша по CPU —
> по CPU он ничего не показывает.

# Этап 2: настоящие int4-идентификаторы — расширение `uidfts`

Прокси первого этапа (base36-строки в обычном `tsvector`) упирается в то, что
ядро всё равно сравнивает строки. На втором этапе сделан минимальный C-extension
с собственными типами; словарь и парсер текста пока не делаются — вместо них
внешний «костыль» на SQL.

## Что сделано

| Компонент | Где | Суть |
|---|---|---|
| `uidvector` | [ext/uidfts/uidvector.c](ext/uidfts/uidvector.c) | аналог `tsvector`: `int32 lexid[n]` (отсортирован) + `uint32 posend[n]` + `WordEntryPos pos[]`. 8 байт на лексему + 2 байта на позицию |
| `uidquery` | [ext/uidfts/uidquery.c](ext/uidfts/uidquery.c) | аналог `tsquery`: тот же бинарный формат `QueryItem`, id лексемы в `valcrc`, без строковой области. Синтаксис как у tsquery: `'12 & (37 \| !5) <-> 8:AB'`. Разбор — ядровым `parse_tsquery()`, вычисление — ядровым `TS_execute()` (AND/OR/NOT/фразы работают без изменений) |
| `@@` | uidvector.c | бинарный поиск по `int32` вместо `tsCompareString()` |
| `ts_rank`, `ts_rank_cd` | [ext/uidfts/uidrank.c](ext/uidfts/uidrank.c) | порт `tsrank.c` из PG14 1:1, заменён только поиск лексемы и доступ к позициям. Все сигнатуры (веса, флаги нормализации) |
| конструктор | `uidvector(lexids int4[], positions int4[])` | «пара массивов»: i-й элемент = лексема `lexids[i]` на позиции `positions[i]` |
| костыль text→ids | [sql/uid/10_uid_crutch.sql](sql/uid/10_uid_crutch.sql) | `tsv_to_uidv(tsvector)`, `tsq_to_uidq(tsquery)` через `lex_dict`; разбор/стемминг — ядровой конфигурацией `english` |

Не сделано (сознательно, следующий шаг): GIN/GiST-опклассы, словари и парсер,
префиксный поиск (`:*`), `setweight`/`strip`/`ts_headline`, бинарный send/recv.


## Интерпретация

1. **Ускорение прокси было целиком за счёт размера, а не CPU.** У прокси
   net ≈ x0.85–1.18, т.е. сами функции не ускорялись — строки остались строками.
   Настоящие int4 ускоряют чистый CPU `@@` и `ts_rank` в **2.0–2.7 раза**.

   > **Проверено на этапе 2.1.** Оценка «net» выше получена вычитанием и шумная.
   > Точный замер подтверждает вывод: у прокси инструкций на 0–3% больше, чем у
   > tsvector. У `uidvector` инструкций в 1.9–2.4 раза меньше (`@@`, `ts_rank`),
   > время на inline-данных — в 2.6–5.5 раза меньше.
2. **Размер даёт порог TOAST.** На этом корпусе (50–200 слов) 43% tsvector-ов
   превышают ~2 КБ и уходят в TOAST, а uidvector — почти никогда. Отсюда
   x5 на выборке значения. Эффект зависит от корпуса: на длинных документах в
   TOAST уйдёт и uidvector, и выигрыш сведётся к пропорции размеров (~0.68).
   Поэтому «end-to-end» x3.9–4.6 надо считать верхней оценкой для коротких
   документов, а net x2 — оценкой, переносимой на другие корпуса.

   **Проверка с `body` в той же строке** (реалистичная раскладка, как в `docs`).
   Порог TOAST (~2 КБ) считается на весь кортеж, а не на одно поле: `body`
   (~1.1 КБ) + вектор превышают его почти всегда, и наружу выносится самое
   большое поле — вектор. Сжатие pglz на этом корпусе не срабатывает ни для
   `body`, ни для векторов. В самой `docs` на 500K строк лежит 829K вынесенных
   значений (tsv и tsv_int почти во всех строках). Те же 20K документов в
   таблицах `(id, body, вектор)`:

   | | tsv, ms | uidv, ms | x |
   |---|---|---|---|
   | TOAST таблицы | 36 MB | 21 MB | |
   | detoast | 38.2 | 30.8 | 1.24 |
   | `ts_rank` single | 42.4 | 32.5 | 1.30 (net 4.2 → 1.7 ms, x2.5) |
   | `ts_rank` and2 | 44.5 | 33.2 | 1.34 (net 6.3 → 2.4 ms, x2.6) |

   Т.е. x5 на detoast — артефакт узкой таблицы. При тексте в той же строке
   выигрыш end-to-end ~x1.3, выигрыш чистого CPU (x2+) сохраняется.

   > **Уточнено на этапе 2.2.** «Почти всегда» — неточно: с `body` в строке в
   > TOAST вынесено 76.9% tsvector, 69.1% прокси и 62.4% uidvector (подсчёт по
   > TOAST-таблицам). Чтение из TOAST происходит *внутри* вызова функции
   > (`PG_GETARG_*` → `detoast_attr`), стоит ~15–17 тыс. инструкций и составляет
   > 86–97% стоимости вызова. См. [Этап 2.2](#этап-22-toast-внутри-вызова-и-топ-k-запрос).
3. **`ts_rank_cd` для многотерминных запросов почти не ускоряется (net x1.13).**
   Его время определяют не сравнения лексем, а накладные расходы алгоритма:
   `palloc0(sizeof(QueryRepresentationOperand) * query->size)`, где каждый
   операнд содержит `pos[MAXENTRYPOS]` = 32 КБ, т.е. ~96 КБ memset на вызов для
   запроса `a & b`, плюс `TS_execute` на каждой позиции в `Cover()`. Это общий
   для tsvector и uidvector резерв оптимизации, не связанный с id.

   > **Проверено на этапе 2.1 — подтверждено.** `memset` занимает 32 793
   > инструкции на вызов для одного терма и 98 390 (= 3 × 32 КБ) для `a & b` и
   > `a <-> b` — 95–97% всех *инструкций* `ts_rank_cd`, одинаково для всех трёх
   > представлений. Блок больше 8 КБ, поэтому `palloc` каждый раз идёт в
   > `malloc`/`free`. Часть про `TS_execute` в `Cover()` не подтвердилась: на этой
   > нагрузке это 4–8 инструкций на вызов, т.к. документов, где встречаются оба
   > терма, почти нет. По *времени* доля `memset` меньше — ~50–75%: callgrind
   > считает `rep stosb` по одной инструкции на байт (см. оговорку в итогах 2.1).

### Итог: что оптимизируется, а что нет

**base36-прокси (строки фиксированной длины 4):**
* Вычисления — **не оптимизирует.** Инструкций на 0–3% больше, чем у tsvector, во
  всех 9 сценариях; сравнений строк и шагов поиска столько же.
* Промахи кэша данных — **оптимизирует**: в 4 раза меньше промахов L1D и LL.
  Это единственное измеренное различие с tsvector, и от него ускорение по
  времени x1.07–1.35 на inline-данных. Почему данные прокси дают меньше промахов
  (меньший вектор, другой порядок лексем), отдельно не изолировалось.
* Размер / TOAST — **оптимизирует** (−19% размера, этап 1 и этап 2).

**uidvector (int4):**
* Сравнение строк — **устранено полностью** (≈380–840 инструкций на вызов → 0).
* Бинарный поиск лексемы — в **1.8–2.5 раза** меньше инструкций.
* `@@` — в **2.1–2.4 раза** меньше инструкций, в **3.3–5.5 раза** быстрее.
* `ts_rank` — в **1.9 раза** меньше инструкций, в **2.6–3.3 раза** быстрее.
* Промахи кэша — на уровне прокси (в 4–7 раз меньше, чем у tsvector).
* Размер — −32% (этап 2).

**Не оптимизируется ни тем, ни другим:**
* `ts_rank_cd`: основная стоимость — `memset` рабочего массива
  `QueryRepresentationOperand` (32 КБ на каждый узел запроса, включая
  операторы), плюс `malloc`/`free` на каждый вызов. От представления лексем не
  зависит. По инструкциям это 95–97%, по времени — ~50–75% (см. оговорку ниже).
  Остальное — тот же поиск лексем, что в `ts_rank`; его uidvector сокращает так
  же, отсюда x1.0–1.11 у прокси и x1.25–1.33 у uidvector.

> **Оговорка про `memset` и callgrind.** Для блоков больше
> `__x86_rep_stosb_threshold` (~2 КБ) glibc обнуляет память одной инструкцией
> `rep stosb`, которую процессор выполняет со скоростью 32–64 байта за такт.
> Valgrind считает каждую итерацию `rep` отдельной инструкцией — по одной на
> байт: 32 793 = 32 768 + 25, 98 390 = 3 × 32 768 + 86. Поэтому доля `memset` в
> инструкциях сильно завышена относительно времени. Оценка доли по времени —
> разность `ts_rank_cd` и `ts_rank` (поиск лексем у них одинаковый), нс на вызов:
>
> | | `ts_rank_cd` | `ts_rank` | разность (память + `Cover`) | доля |
> |---|---|---|---|---|
> | single, tsvector | 890 | 431 | 459 | ~52% |
> | single, uidvector | 670 | 147 | 523 | ~78% |
> | and2, tsvector | 2 764 | 670 | 2 094 | ~76% |
> | and2, uidvector | 2 203 | 257 | 1 946 | ~88% |
>
> Это оценка по разности, а не прямой замер `memset`. Почему 96 КБ (запрос из
> двух слов) обнуляются в ~4 раза дольше, чем 32 КБ, отдельно не проверялось.
> Остальные выводы по инструкциям этим не затронуты: в сравнении строк, поиске
> лексем и чтении из TOAST `rep`-инструкций нет (копирование кусков TOAST идёт
> через `memcpy` без `rep`, ~53 инструкции на вызов).
* Работа исполнителя, вызов функции, `palloc` в `ts_rank`
  (`прочее` ≈ 230–300 инструкций, `память` ≈ 140–380) — одинаковы.

## Этап 2.2: TOAST внутри вызова и топ-k запрос

**Вопросы.** (1) Сколько в одном вызове `@@` / `ts_rank` / `ts_rank_cd` стоит
чтение вектора из TOAST по сравнению с самим вычислением. (2) Сколько раз на
строку вектор читается из TOAST в типичном запросе
`WHERE col @@ q ORDER BY ts_rank(col, q) DESC LIMIT 10` и сколько это стоит.

**Почему это важно.** Чтение из TOAST выполняет не исполнитель, а сама функция:
`PG_GETARG_TSVECTOR` / `PG_GETARG_UIDVECTOR` → `pg_detoast_datum` → `detoast_attr`.
Готовое значение между вызовами не кэшируется, поэтому `@@` и `ts_rank` в одном
запросе читают его каждый сам.

**Методика.** Тот же приватный кластер и те же 20K документов, что в 2.1, но
хранение обычное (`STORAGE EXTENDED`), две раскладки
([sql/uid/21_toast_tables.sql](sql/uid/21_toast_tables.sql)):
`n_*(id, вектор)` — вектор один в строке; `b_*(id, body, вектор)` — с текстом
документа, как в `docs`. На `b_tsv` и `b_tsv_int` — GIN. Профили callgrind
([tools/stage22_callgrind.sh](tools/stage22_callgrind.sh)); число вызовов и
инклюзивная стоимость функций считаются прямо по записям `calls=` файла профиля
([tools/cg_calls.py](tools/cg_calls.py)), для топ-k запроса чтения из TOAST
разнесены по вызывающим функциям (`--separate-callers=3`). Отчёт —
[tools/stage22_report.py](tools/stage22_report.py), полный вывод:
`results/uid/stage22_callgrind_report.md`.

Сколько значений вынесено в TOAST (точный подсчёт по TOAST-таблицам):

| | tsvector | прокси | uidvector |
|---|---|---|---|
| `(id, вектор)` | 42.8% | 22.1% | 0.1% |
| `(id, body, вектор)` | 76.9% | 69.1% | 62.4% |

### A. Один вызов функции, инструкций (запросы `and2`)

«TOAST на вызов» — инклюзивная стоимость `detoast_attr`, делённая на число
вызовов функции; «вычисление» — остальное.

| Раскладка | Функция | Вариант | одно чтение из TOAST | **TOAST на вызов** | **вычисление** | **всего** | доля TOAST | x к tsvector |
|---|---|---|---|---|---|---|---|---|
| (id, вектор) | `@@` | tsvector | 16 853 | 7 214 | 833 | 8 047 | 90% | 1.00 |
| | | прокси | 16 567 | 3 666 | 855 | 4 521 | 81% | 1.78 |

### Выводы этапа 2.2

1. **Чтение из TOAST — самая дорогая операция в вызове.** Одно чтение стоит
   15–17 тыс. инструкций независимо от представления: 1.25 КБ uidvector лишь
   на 6% дешевле 1.85 КБ tsvector — цена в поиске по индексу TOAST-таблицы, а не
   в объёме. Это в 8 раз больше всего `ts_rank` и в 20 раз больше `@@`.
2. **С текстом документа в строке TOAST — 86–97% стоимости `@@` и `ts_rank`.**
   Ускорение вычисления в 2 раза (этап 2.1) почти не видно: итог x1.35–1.38 по
   инструкциям и x1.24–1.25 по времени. Выигрыш uidvector здесь в основном
   от того, что меньший вектор реже выносится в TOAST (62% строк против 77%).
3. **В узкой таблице картина обратная:** uidvector практически не попадает в
   TOAST, и `@@` дешевле в 26 раз, `ts_rank` — в 9.5 раза. Так что результат
   сильно зависит от схемы хранения; ключевой параметр — уместится ли вектор
   в строку.
4. **Двойное чтение из TOAST подтверждено, но вклад мал.** При seq scan каждая
   совпавшая строка читается дважды (`@@`, затем `ts_rank`): 3 396 повторных
   чтений против 76 865 в `@@` на single-запросах, ~3.6% инструкций. С GIN без
   перепроверки (`single`, `and2`) повторов нет — `@@` не вызывается; с фразой
   GIN перепроверяет кандидатов через `@@`, и совпавшие строки снова читаются
   дважды. Вклад станет заметным только для запросов, совпадающих с большой
   долей таблицы при перепроверке.
5. **Индекс важнее представления:** топ-10 через GIN в 14–150 раз быстрее
   seq scan и в 11–28 раз дешевле по инструкциям. Сравнивать uidvector с
   tsvector «запрос целиком» без GIN для uidvector нельзя.

## Следующие шаги

* **`ts_rank_cd`: выделять позиции по фактическому числу вхождений**, а не
  `MAXENTRYPOS` = 16384 на узел. Сейчас это ~50–75% времени функции; правка не
  связана с id и применима к ядру (потенциальный патч в PostgreSQL).
* **GIN-опкласс для `uidvector`** (ключи — `int4`, `extractQuery`/`triConsistent`
  по образцу `gin_extract_tsquery`). После этапа 2.2 это главный пробел:
  индекс даёт x14–150, и без него нельзя сравнить запрос целиком.
* **Удержание вектора в строке (без TOAST):** чтение из TOAST — 86–97% стоимости
  вызова. Проверить компактный формат позиций, `toast_tuple_target`,
  хранение векторов отдельно от текста.
* Компактнее хранить позиции/смещения (`uint16 npos` или varbyte-дельты) —
  оценить, сколько ещё даёт размер.
* Словарь `text → id` внутри PostgreSQL (таблица/shared hash) и
  `to_uidvector(regconfig, text)` / `to_uidquery(...)`, чтобы убрать костыль.
