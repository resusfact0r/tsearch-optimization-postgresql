# FTS uid experiment - замена строковых лексем на целочисленные идентификаторы

## Мотивация

PostgreSQL FTS хранит лексемы в `tsvector` как переменные строки. При поиске и ранжировании
документов ядро делает бинарный поиск по лексемам с побайтовым сравнением строк. Гипотеза:

> Если заменить строковые лексемы на фиксированные 4-байтные целочисленные идентификаторы,
> то уменьшится размер `tsvector`, ускорится проход по GIN/GIST, и - главное - ускорятся
> функции `ts_rank` / `ts_rank_cd`, которые индекс не используют и работают целиком на CPU.

Настоящий C-extension пока не пишется. Вместо этого делается прокси: лексемы
заменяются 4-символьными строками из алфавита `0-9a-z` (base36). Ширина ключа та же -
4 байта, - поэтому прокси является честным нижним порогом для реального int4-extension.

---

## Методология

### Прокси-кодирование

Вместо настоящего `int4` используется строка из 4 символов алфавита `0-9a-z` (36 символов,
36^4 = 1 679 616 уникальных значений). Алфавит выбран строчным потому, что `to_tsquery('simple', ...)`
приводит токены к нижнему регистру - заглавные символы вызывали бы коллизии.

Пример: лексема `"initi"` (самая частая в корпусе) получает id 1 -> encoded = `"0001"`.

Позиции и веса слов в `tsvector` сохраняются полностью, поэтому прокси-вектор
семантически эквивалентен исходному: проверяется верификационным шагом.

### Параметры бенчмарка

| Параметр | Значение |
|---|---|
| PostgreSQL | 14.23 |
| Корпус | 10 000 документов, 50-200 слов, синтетика из `/usr/share/dict/words` |
| Конфигурация FTS | `english` (для baseline), `simple` (для прокси-запросов) |
| JIT | выключен (`SET jit = off`) |
| Параллелизм | выключен (`max_parallel_workers_per_gather = 0`) |
| Кэш | тёплый (всё в `shared_buffers`) |
| Повторений | 10 прогонов на каждую точку, медиана |
| GIN vs GIST | замеряются раздельно: перед GIN-замером дропается GIST, и наоборот |

### Запросная нагрузка

- **single** - 500 запросов по одному термину (топ-500 по частоте в корпусе)
- **and2** - 200 AND-запросов из двух термин
- **phrase** - 200 фразовых запросов (`<->`)

Для каждого текстового запроса строится его прокси-двойник: лексемы заменяются
закодированными id, конфигурация меняется с `english` на `simple`.

## Интерпретация результатов

### Ранжирование: гипотеза подтверждается, эффект устойчив

`ts_rank` и `ts_rank_cd` ускоряются на **8-44%** как при тёплом, так и при холодном кэше.
Ускорение при холодном кэше даже чуть выше: меньший `tsvector` -> меньше страниц читается
с диска при TABLESAMPLE-сканировании + быстрее CPU-сравнения. Это сугубо CPU-эффект,
не зависящий от I/O - функции ранжирования индекс не используют.

### GIN: разница в пределах шума на 10K корпусе

Однотерминный GIN-поиск показывает x0.99-1.00 - практически без разницы. Причина: GIN
posting-листы по размеру примерно одинаковы (7968 vs 7856 kB, разница 1.4%), а 10K документов
полностью помещаются в кэш. Значимая разница ожидалась на 500K+ документов, предполагалось что индекс не
помещается в память и I/O-чтения более коротких posting-листов дадут измеримый выигрыш, но по результату выигрыш получился небольшой: x1.00-1.04 

### GIST: структурное замедление для AND-запросов

GIST замедляется для AND/phrase как в тёплом (x0.78), так и в холодном (x0.80) режиме.
Это не I/O-артефакт - разрыв одинаков при любом состоянии кэша. Скорее всего здесь структурная причина:
GIST использует сигнатурное хэширование лексем для построения bitmap. Base36-идентификаторы
вида `0001`, `0002`, … сконцентрированы в начале алфавита и хуже распределяются по
хэш-пространству, чем естественные английские слова. Это приводит к большему числу
false-positive при проверке AND-условия и дополнительным heap-fetches для recheck.

### Ограничение прокси

Прокси использует строки base36 (4 байта содержимого + 1 байт varlena-заголовок = 5 байт)
вместо настоящего `int4` (4 байта без заголовка). Кроме того, сравнение строк - это `memcmp`,
тогда как int4 сравнивается одной машинной инструкцией. Поэтому если прокси даёт X% ускорения - реальный int4-extension даст не меньше X%.

# Этап 2: настоящие int4-идентификаторы — расширение `uidfts`

Прокси первого этапа (base36-строки в обычном `tsvector`) упирается в то, что
ядро всё равно сравнивает строки. На втором этапе сделан минимальный C-extension
с собственными типами; словарь и парсер текста пока не делаются — вместо них
внешний «костыль» на SQL.

## Что сделано

| Компонент | Где | Суть |
|---|---|---|
| `uidvector` | [ext/uidfts/uidvector.c](ext/uidfts/uidvector.c) | аналог `tsvector`: `int32 lexid[n]` (отсортирован) + `uint32 posend[n]` + `WordEntryPos pos[]`. 8 байт на лексему + 2 байта на позицию |
| `uidquery` | [ext/uidfts/uidquery.c](ext/uidfts/uidquery.c) | аналог `tsquery`: тот же бинарный формат `QueryItem`, id лексемы в `valcrc`, без строковой области. Синтаксис как у tsquery: `'12 & (37 \| !5) <-> 8:AB'`. Разбор — ядровым `parse_tsquery()`, вычисление — ядровым `TS_execute()` (AND/OR/NOT/фразы работают без изменений) |
| `@@` | uidvector.c | бинарный поиск по `int32` вместо `tsCompareString()` |
| `ts_rank`, `ts_rank_cd` | [ext/uidfts/uidrank.c](ext/uidfts/uidrank.c) | порт `tsrank.c` из PG14 1:1, заменён только поиск лексемы и доступ к позициям. Все сигнатуры (веса, флаги нормализации) |
| конструктор | `uidvector(lexids int4[], positions int4[])` | «пара массивов»: i-й элемент = лексема `lexids[i]` на позиции `positions[i]` |
| костыль text→ids | [sql/uid/10_uid_crutch.sql](sql/uid/10_uid_crutch.sql) | `tsv_to_uidv(tsvector)`, `tsq_to_uidq(tsquery)` через `lex_dict`; разбор/стемминг — ядровой конфигурацией `english` |

Не сделано (сознательно, следующий шаг): GIN/GiST-опклассы, словари и парсер,
префиксный поиск (`:*`), `setweight`/`strip`/`ts_headline`, бинарный send/recv.

## Корректность

* Регрессионный тест ([ext/uidfts/sql/uidfts.sql](ext/uidfts/sql/uidfts.sql)):
  лексемы `a..i` ↔ id `1..9` (порядок строк = порядку id), 300 случайных
  документов с весами × 21 запрос (NOT, OR, фразы `<N>`, веса, пустой документ,
  документ без позиций). `@@`, `ts_rank`, `ts_rank_cd` при всех 64 флагах
  нормализации и пользовательских весах совпадают с ядром **побитово**.
* На корпусе ([sql/uid/12_uid_verify.sql](sql/uid/12_uid_verify.sql)): число лексем
  совпадает во всех 500 000 документов; 5 000 документов × 900 запросов = 4.5M пар —
  0 расхождений по `@@`, `ts_rank` и `ts_rank_cd` побитово равны; полные счётчики
  совпадений по корпусу совпадают.

### Найденная ошибка в нагрузке этапа 1

`06_bench_search.sql` строил `q_orig` как `to_tsquery('english', lexeme)`, хотя
`lexeme` из `lex_dict` уже прошла стемминг — стеммер применялся повторно
(`advis` → `advi`). У 47 из 900 запросов baseline искал несуществующую лексему,
а прокси — настоящую. На цифры этапа 1 это почти не повлияло (замерялся только
первый запрос каждого типа, qid 1/501/701 — корректные). Скрипты 05/06 исправлены
(`to_tsquery('simple', quote_literal(lexeme))`); в текущей БД `bench_queries` не
пересоздавалась, uid-бенчмарк такие запросы пропускает.

## Интерпретация

1. **Ускорение прокси было целиком за счёт размера, а не CPU.** У прокси
   net ≈ x0.85–1.18, т.е. сами функции не ускорялись — строки остались строками.
   Настоящие int4 ускоряют чистый CPU `@@` и `ts_rank` в **2.0–2.7 раза**.
2. **Размер даёт порог TOAST.** На этом корпусе (50–200 слов) 43% tsvector-ов
   превышают ~2 КБ и уходят в TOAST, а uidvector — почти никогда. Отсюда
   x5 на выборке значения. Эффект зависит от корпуса: на длинных документах в
   TOAST уйдёт и uidvector, и выигрыш сведётся к пропорции размеров (~0.68).
   Поэтому «end-to-end» x3.9–4.6 надо считать верхней оценкой для коротких
   документов, а net x2 — оценкой, переносимой на другие корпуса.

   **Проверка с `body` в той же строке** (реалистичная раскладка, как в `docs`).
   Порог TOAST (~2 КБ) считается на весь кортеж, а не на одно поле: `body`
   (~1.1 КБ) + вектор превышают его почти всегда, и наружу выносится самое
   большое поле — вектор. Сжатие pglz на этом корпусе не срабатывает ни для
   `body`, ни для векторов. В самой `docs` на 500K строк лежит 829K вынесенных
   значений (tsv и tsv_int почти во всех строках). Те же 20K документов в
   таблицах `(id, body, вектор)`:

   | | tsv, ms | uidv, ms | x |
   |---|---|---|---|
   | TOAST таблицы | 36 MB | 21 MB | |
   | detoast | 38.2 | 30.8 | 1.24 |
   | `ts_rank` single | 42.4 | 32.5 | 1.30 (net 4.2 → 1.7 ms, x2.5) |
   | `ts_rank` and2 | 44.5 | 33.2 | 1.34 (net 6.3 → 2.4 ms, x2.6) |

   Т.е. x5 на detoast — артефакт узкой таблицы. При тексте в той же строке
   выигрыш end-to-end ~x1.3, выигрыш чистого CPU (x2+) сохраняется.
3. **`ts_rank_cd` для многотерминных запросов почти не ускоряется (net x1.13).**
   Его время определяют не сравнения лексем, а накладные расходы алгоритма:
   `palloc0(sizeof(QueryRepresentationOperand) * query->size)`, где каждый
   операнд содержит `pos[MAXENTRYPOS]` = 32 КБ, т.е. ~96 КБ memset на вызов для
   запроса `a & b`, плюс `TS_execute` на каждой позиции в `Cover()`. Это общий
   для tsvector и uidvector резерв оптимизации, не связанный с id.
